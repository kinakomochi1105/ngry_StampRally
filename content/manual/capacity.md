## データ量の目安

| 項目 | 1000人×6地点の場合 |
| --- | --- |
| 参加者レコード | 1000件 |
| 押印レコード | 最大6000件 |
| 混み具合の集計 | 直近10分ぶんだけ |
| CSV出力 | 1回あたり最大10000人 |

データ量そのものは小さく、SQLite（libSQL）で問題になる規模ではありません。詰まるのは**通信と同時接続**です。

## リクエストが発生する場面

- 参加登録時。
- スタンプ帳の表示時。
- QRの読み取り（押印）時。
- ログイン中は**60秒ごと**に匿名の混み具合を更新。
- 管理画面は50人ごとのページ取得。

> [!注意]
> 1000人の来場と1000人の同時接続は別の話です。混み具合の定期更新があるため、**画面を開いたままの人数**が実効的な同時接続数になります。開場直後と終了直前に山が来ます。

## 事前に測ること

- [ ] 本番相当の構成で、想定同時接続の負荷試験を行う
- [ ] 会場Wi-Fiの同時接続上限を管理者に確認する
- [ ] 各設置場所で携帯回線の電波が届くか現地で確認する
- [ ] iPhone Safari / Android Chrome でカメラが動くことを実機で確認する
- [ ] 配信基盤側のレート制限・上限を設定する

ローカルでの試験は本番の性能保証になりません。

## 混雑表示の仕組みと限界

有効なQRが読まれるたびに、場所IDと時刻だけを短期集計テーブルに記録します。個人ハッシュやニックネームは混雑集計にコピーしません。

| 直近10分の読み取り数 | 表示 |
| --- | --- |
| 0〜2件 | 空いている |
| 3〜7件 | 少し動きあり |
| 8件以上 | 混雑 |

10分を過ぎた件数は表示から外れます。**待ち時間や現在地を示すものではありません。** 参加者に「混雑」と出ていても実際は空いていることがあります。案内の根拠にするなら、係員の目視を優先してください。

## 詰まったときの手当て

- 特定スポットに行列 → QR台紙を増やす（同じ内容で複数枚）。掲示位置を広げる。
- 会場Wi-Fiが飽和 → 携帯回線の利用を案内する。
- 配信が重い → 混み具合の更新が止まっても押印はできます。画面の再読み込みを案内します。
- 改善しない → 紙の台紙へ切り替える判断を早めに（[紙の台紙と代替手段](./paper-backup.md)）。

## 地点数を変えるときの影響

公開中の地点数はコンプリートの条件に直結します。開催中に増やすと、すでにコンプリートしていた人が未達成に戻ります。減らすと、未達成だった人が一斉にコンプリートします。**開催中の変更は避けてください。** どうしても必要なら、本部で影響を確認してから行います（[設置場所とQRコードの設計](./spots-qr.md)）。
